Where this board differed from your recipe:

  • User-site packages leak into the CUDA env. An earlier pip install --user left numpy 2.2.6, tensorflow and protobuf 7 in ~/.local, which sits on sys.path ahead of the system packages. The vla alias now sets PYTHONNOUSERSITE=1.
  • CUDA torch.linalg fails with an undefined cuSOLVER symbol. The torch 2.8.0 wheel expects a newer cuSOLVER than JetPack 6.2's 11.6.4. Matmul, convolution and attention are unaffected, so matrix decompositions will run on the CPU.
  • The current torch wheel no longer links cuDSS. We kept the cuDSS step to match your recipe. It is isolated and harmless.
  • A guard against the CPU-torch accident. A constraints file inside the CUDA venv pins torch, torchvision, torchaudio and numpy<2, so a pip install that would replace the Jetson wheel now fails loudly.

Exact package sets are committed in hardware/envs/, and requirements.txt is pinned, including the torch wheel's sha256.

4. Measurement harness and first measurements

benchmarks/hello_latency.py now samples the INA3221 rails, the GPU clock and the junction temperature in a thread that covers exactly the timed loop. It reads sysfs directly, so it needs no root and no jtop, and it still runs on the workstation. Every record carries p50, p90 and p99 latency, peak memory, mean and peak power per rail, energy per inference, power mode, clock state, GPU clock range, peak temperature and the git commit.

The model is still the stand-in 4-layer convnet, so these numbers validate the harness. They are not a VLA baseline. All 25 records are committed in results/ against clean commits. The first 13 ran with the board's default clock scaling. The other 12 ran later on 2026-09-28 with the clocks locked, through a script that switches the power mode for each check and then restores the board. The desktop session was running throughout, at a load average of about 1.3 to 2.1 on 6 cores.

What the default clock scaling hid. Left to itself, the governor answers extra work with higher clocks and more power, so latency stayed flat from 112 to 672 px while board power rose from 6.5 W to 14.9 W. With the clocks locked, latency follows the work. Up to 336 px it holds at the stand-in model's fixed overhead of about 1.15 ms, and above that it climbs with the pixel count: 2.29 times longer from 1344 to 2048 px, for 2.32 times the pixels.

Locking also removed most of the jitter. At 224 px, over 3000 steps each, the worst 1% went from 4.90 ms to 1.38 ms. Large images took about a quarter less time: 13.8 ms down to 9.9 ms at 1344 px, and 30.7 ms down to 22.7 ms at 2048 px. That happened although the GPU ran at 1020 MHz in both cases, so another clock was scaling, most likely the memory clock. jetson_clocks locks it too, but we can't read it without root. The one near-tie is 672 px, where the medians are 2.5 and 2.8 ms but the worst case halves from 5.9 to 3.2 ms. The price of locking is 1 to 2 W more at small sizes.

  • From MAXN SUPER to 15 W the GPU clock drops 40% but latency rises only 27%, so this workload isn't limited by the GPU clock alone.
  • The 25 W mode has the slowest CPU (1344 MHz, against 1497 in 15 W), and it was the slowest mode at small sizes, where per-step CPU overhead dominates. That matters for a pipeline with CPU-side preprocessing.
  • No run throttled. The chip peaked at 61.5 °C.

What this means for the project:

  • Every experiment runs with the clocks locked. Default scaling adds jitter and understates the board.
  • We still need to choose the power mode for the main sweep. MAXN SUPER with locked clocks was fastest, with no throttling in these short runs, though longer runs of the real model need watching; the harness flags a locked clock that drops. 15 W gives about the same energy per step, which fits a battery-powered story.
  • Energy per inference belongs in the trade-off curves next to latency.

5. Is the Hiwonder SO-ARM101 kit right for this project?

We had planned to buy the Hiwonder SO-ARM101 advanced kit, $459.99 on hiwonder.com and also sold on Amazon. Checking it against Hiwonder's own manual and product page on 2026-09-28 showed that it differs from the reference SO-101 in ways that matter for this project.

Evidence it would work

  • Hiwonder says its HM-series servos use the STS3215's protocol and register map.
  • Its driver gives the HX-30HM the STS3215's model number, 777, which is the number LeRobot's Feetech driver checks on connect.
  • Hiwonder's manual drives the arms with the standard so101_follower and so101_leader types and the [feetech] extra.

Evidence for caution

  • Hiwonder's two pull requests adding HX-30HM support to LeRobot, #3871 and #3872, were closed without being merged. No LeRobot release lists these servos.
  • No model number is published for the leader's HX-10HM.
  • We found nothing showing the kit on stock LeRobot 0.4.4 or 0.5.x, or with so101_unified_teleop.py.
  • The uniform 1:147 leader should move easily, but it may not hold its own pose the way the reference leader's 1/345 shoulder does.
